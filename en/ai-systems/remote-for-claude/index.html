AI Systems · Product Case Study

DeskRelay

An open-source self-host tool for driving the claude CLI on a user's own PC from a browser or optional mobile shell. The site backend serves the UI and registered devices; the PC connector daemon owns local execution, files, shell, Git, MCP, and Claude authentication.

Role

Designed and implemented the product architecture, connector runtime, self-host backend, frontend UX, device lifecycle, screenshots, and documentation.

Problem

Agent work is most useful on a machine with the user's repo, shell, and tokens. But that also pins the workflow to one keyboard.

Approach

Keep execution local. Run a self-host site backend, register each PC by daemon URL and token, and expose a narrow browser/mobile control surface over a private network.

Status

Open-source self-host product: PC server scripts, site token login, local connector auto-registration, Settings -> Devices validation, remote chat, diagnostics, and docs are wired.

§ 02 · Architecture

Remote UI, local execution

The site should feel like a product, but the sensitive execution surface stays on the user's PC.

End-to-end path
Browser → Site Backend → Connector Daemon → Claude CLI

The backend serves the UI and device registry. Work, files, and credentials stay on the controlled PC.

BrowserSolidJS UI, chat, settings, approvals

hubProduct shell outside, runtime authority inside the user's PC.
System slices

Frontend. SolidJS + Vite SPA with locale files, device picker, chat, diagnostics, approval modal, workspace picker, image preview, and optional Capacitor wrapper.

Site backend. Hono/Bun self-host process. The PC server script starts the backend, prints a site token, serves the browser UI, and manages registered connector daemon URLs.

Connector. Bun daemon/CLI on each controlled PC. It exposes an authenticated daemon URL, reports /status, owns workspace roots, and keeps files, shell, Git, MCP, and Claude auth on that PC.

Operations. The manual recommends Tailscale, WireGuard, private LAN, or VPN access and warns against exposing connector daemon ports directly to the public internet.

§ 03 · Device lifecycle

Device registration is a product feature, not an admin chore

The hard part is not only adding a device. It is making the browser, self-host backend, and connector daemon agree on what is reachable, authorized, and safe to operate.

Register

Daemon URL, label, token

A target PC runs the connector daemon with private-network host/port and workspace roots. Settings -> Devices registers its daemon URL, label, and daemon token.

Validate

Status check before use

The backend checks the connector /status endpoint and refuses bad URLs or tokens before the device becomes selectable.

Operate

Switch, diagnose, continue

The sidebar switches devices, settings expose connection diagnostics, and sessions can continue, fork, or start fresh from selected workspace directories.

§ 04 · Trust boundary

Private-network first, local authority stays local

The README/manual boundary is intentionally plain: there is no hosted DeskRelay account, payment flow, managed relay, or required app package. The user runs the site backend and connector daemon themselves, preferably over Tailscale, WireGuard, private LAN, or VPN.

That distinction matters. I prefer a product that states the boundary honestly, with the screenshots, docs, and architecture aligned, over a privacy claim that the system shape does not enforce.
