[ MOD.01 ] JACOBIAN IK vr robot · robotics

// jacobian ik solver

In-house Jacobian IK solver.

Robotics Damped Least Squares 6-DOF Realtime

An inverse-kinematics solver for controlling an industrial 6-axis robot in real time from 6-DOF VR controller input. I built stable behavior that does not diverge near singularities, while reducing the dependency on RoboDK.

Related case · VR Robot ↗
// demo — live demo footage
// problem

Given a target pose (TCP), you have to solve backward for each joint angle — but the solution may be multiple or non-existent. Especially near a singularity, where the arm stretches into a straight line, a pure matrix-inverse approach makes joint velocities blow up and the robot jerks. Depending on an external solver (RoboDK) every frame also hurt real-time performance and portability.

// approach

I solved it with Damped Least Squares rather than the Jacobian transpose. As the configuration approaches a singularity, I raise the damping, trading a little accuracy so the solution does not diverge. VR input maps directly to the solver's target pose, and invalid commands are filtered out before they reach the robot.

[ MOD.02 ] BIM CROSS-SECTION watchbim · runtime geometry
// bim runtime cross-section

Runtime cross-section engine.

Computational Geometry Mesh Slicing Custom Hit Engine 2D Viewer

An operational need that off-the-shelf BIM tools could not meet — I built the ability to generate a cross-section from any plane at runtime and to measure and analyze the result in a 2D viewer. For picking and hover on large models, I used a custom hit engine instead of the standard Raycast.

Related case · WatchBIM ↗
// demo — live demo footage
// problem

Operators say, "I want to cut here, see the cross-section, and measure dimensions," but ordinary BIM viewers do not provide runtime cross-section generation or real-time 2D analysis. On top of that, on large models reliable selection was hard with the standard Physics.Raycast alone.

// approach

Off-the-shelf BIM tools fell short here, so I wrote the geometry I needed. The 2D segment-intersection test is implemented with an orientation (cross-product sign) method, and mesh cutting/clipping is built on a computational-geometry library (Habrador — cut-mesh-with-plane · polygon clipping · ear-clipping triangulation). Large vertex passes are parallelized with the Unity Job System and Burst, and the 3D model and 2D viewer share one data model.

// live — drag the canvas · cross-section concept
// code — based on actual implementation (WBExtensions)
// 2D segment-intersection test — orientation (cross-product sign)
int Orient(Pt p, Pt q, Pt r) {
    float v = (q.Y - p.Y) * (r.X - q.X) - (q.X - p.X) * (r.Y - q.Y);
    return v == 0 ? 0 : (v > 0 ? 1 : 2);     // collinear / CW / CCW
}
bool IsIntersect(Pt p1, Pt q1, Pt p2, Pt q2) {
    int o1 = Orient(p1,q1,p2), o2 = Orient(p1,q1,q2);
    int o3 = Orient(p2,q2,p1), o4 = Orient(p2,q2,q1);
    return o1 != o2 && o3 != o4;              // (+ collinear special cases)
}

// large vertex passes: Unity Job System + Burst

// custom editor tooling

Tooling for non-developers.

Editor Scripting 9 EditorWindows Data Mapping Digital Twin

Developers were repeating data mapping, asset registration, and validation whenever the content changed. I built nine EditorWindows so content authors and operators could handle those jobs without opening the code.

Related case · DX Center ↗
// problem

In exhibition and digital-twin operations, the same manual work (data mapping, asset registration, lineup swaps) kept repeating, and a developer had to step in every time. If operators cannot do it themselves, it is not a tool but a bottleneck.

// approach

I made separate screens for data mapping, asset registration, lineup changes, and validation. EditorWindow, SerializedObject, and custom inspectors map external data to scene objects; the same window validates changes and registers Undo before applying them.

// viz — external data → scene-object mapping and validation flow
// code — illustrative code (core pattern)
// core pattern of a non-developer EditorWindow
public class DataMapperWindow : EditorWindow {
    [MenuItem("DXCenter/Data Mapper")]
    static void Open() => GetWindow<DataMapperWindow>("Data Mapper");

    void OnGUI() {
        foreach (var row in mapping)                 // external data → scene object
            row.target = (GameObject)EditorGUILayout.ObjectField(
                row.key, row.target, typeof(GameObject), true);

        if (GUILayout.Button("Validate & Apply") && Validate(mapping)) {
            Undo.RecordObjects(Targets(mapping), "Apply Mapping");
            Apply(mapping);                          // serialize · save
        }
    }
}

[ MOD.04 ] HARDWARE SYNC vr simulators · co-design
// hardware ↔ unity sync

Moving platform, safety interlock.

HW/SW Co-design Motion Platform Safety Interlock Delivery

To shake a scaffold inside VR and make the fall hazard felt, we needed a platform that actually moves. I designed and built a dual-axis scaffold rig myself, synchronized its motion with Unity input, and owned the operator safety interlock as well.

Related case · VR Simulators ↗
// demo — live demo footage
// problem

Software alone cannot train "shaking" and "the sense of losing balance." But once you add a physical rig, the moment the hardware motion and the VR view drift apart, motion sickness and accident risk appear. We needed to align the two precisely and to stop instantly when something goes wrong.

// approach

I designed a 2-axis motion platform and synchronized the hardware sensors/actuators with the Unity simulation in a single loop. The view and the platform tilt move on the same timeline, and I added a safety interlock that stops from both software and hardware when the operating range is exceeded.
